# BOQA v1.5.0 Security + Release Integrity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Seal BOQA v1.5.0 with public security headers, an independently implemented publication-integrity gate, source-first security-audit evidence, explicit release authorization, and exact equality across main/tag/production.

**Architecture:** Preserve BOQA's accepted runtime and authority model. Add one common public-response header policy at the Cloudflare worker edge, keep private-surface headers stricter, add one zero-dependency Node publication checker, version the release workflow to v1.5.0 with manual dispatch and exact tag/SHA equality, and update only truthful release/readiness references. External tools remain methodology/triage only.

**Tech Stack:** Node.js 20, existing Cloudflare Worker, GitHub Actions, existing Playwright/Docker qualification, zero new runtime dependencies.

**Spec:** user handoff “FINAL SECURITY + RELEASE INTEGRITY” plus NVIDIA OpenShell addendum.

## Global Constraints

- No new product features, runtime framework, database, AI authority, autonomy, or backend replacement.
- Do not move or recreate `v1.4.0`.
- `MODEL_OUTPUT != AUTHORIZATION`.
- `OPENSHELL_ADVISOR_OUTPUT != AUTHORIZATION`.
- Current Docker qualification remains canonical for v1.5.0.
- No production probing during the security audit; bounded source/local fixtures only.
- Every security candidate receives an independent verifier before classification.
- Release mutation requires explicit invocation.
- Required release invariant: `RELEASE_TAG_SHA == FINAL_MAIN_SHA`.

## Review Focus

- CSP must not require `unsafe-inline`/eval and must keep `/status/` functional.
- Public JSON/proxy responses and static assets must receive the public policy; hidden/private responses must retain the stronger private policy.
- Publication check must fail on stale v1.4.0 references after promotion, stale readiness date/status, package mismatch, unsupported public claims, and tag/SHA mismatch when a release tag is claimed.
- Release verification must reject ancestor-only relationships.
- Security audit must distinguish release-blocking boundary violations from hardening-only observations.
